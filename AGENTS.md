# Руководство по репозиторию

## Размещение кода

- Серверный код размещайте в `server/`, интерфейс — в `web/`.
- Контракт API описывайте в `api/main.tsp`, результаты генерации храните в `generated/`.
- Тесты размещайте в `tests/`, служебные скрипты — в `scripts/`.
- Не добавляйте результаты сборки из `dist/` в Git.

## Окружение и команды

Используйте mise для окружения и команд проекта. Версии инструментов, переменные окружения и задачи задавайте в `mise.toml`, зависимости приложения фиксируйте в `package.json` и lockfile.

```bash
mise trust
mise install          # установка инструментов
mise run install      # зависимости по lockfile и Git-хуки hk через mise
mise run dev          # запуск фоновых серверов разработки
mise run status       # состояние процессов
mise run logs         # логи
mise run stop         # остановка процессов
mise run build        # сборка сервера и фронтенда
mise run start        # запуск собранного приложения
mise run lint         # запуск линтера
mise run check        # общий прогон проверок
mise run fix          # автоисправления линтера и форматирование
```

## Код и контракт API

Используйте строгий TypeScript, ES-модули и компоненты Mantine. Сохраняйте стиль существующего кода: PascalCase для компонентов и типов, camelCase для функций и переменных. Следуйте конфигурациям TypeScript, oxfmt и Oxlint; не ослабляйте проверки ради прохождения CI.

Изменяйте API через TypeSpec, затем выполняйте `mise run generate`. Добавляйте результаты из `generated/` в коммит, не редактируйте их вручную. Фронтенд должен обращаться к API через сгенерированный SDK.

При обновлении инструментов проверяйте всю цепочку TypeSpec → OpenAPI → SDK, совместимость сервера с контрактом и сборку фронтенда.

## Тестирование и CI

Добавляйте тесты для новой функциональности и регрессий. Используйте Vitest и имена `*.test.ts`; запускайте тесты через `mise run test`. В тестах запуска приложения задавайте таймауты и завершайте созданные процессы даже при ошибке.

Перед PR запускайте `mise run check`. Новые проверки подключайте к этой общей задаче; CI должен вызывать ту же команду. Не изменяйте учебный `.github/workflows/hexlet-check.yml`.

## Коммиты и локальные настройки

Используйте Conventional Commits, например `feat(api): add meeting types`. Следуйте `commitlint.config.cjs`. Настраивайте Git-хуки через hk и вызывайте из них общие проверки проекта.

В заголовке коммита реализации указывайте номер закрываемого тикета, например `feat: запись на свободный слот (#12)`, чтобы GitHub связывал коммит с задачей.

Не добавляйте секреты в Git. Локальные настройки храните в игнорируемом `mise.local.toml`. При смене портов фоновых процессов обновляйте также их `ready_port`.

## Актуальная информация о проекте

За описанием возможностей, ограничений и инструкциями запуска обращайтесь к [README.md](README.md). Обновляйте его вместе с изменениями поведения и настройки приложения. Не записывайте в `AGENTS.md` статус реализации, число тестов, временные ограничения версий и результаты отдельных прогонов.

## Agent skills

Завершив запрошенный этап workflow, представьте результат для ревью пользователя и остановитесь. Следующий этап начинайте по отдельному указанию пользователя. Если пользователь явно запросил несколько этапов, выполните эту последовательность без повторных подтверждений.

### Issue tracker

Задачи и спецификации ведутся в GitHub Issues репозитория `lukyanzhukov/ai-for-developers-project-386`. See `docs/agents/issue-tracker.md`.

### Triage labels
