# Календарь звонков

[![hexlet-check](https://github.com/lukyanzhukov/ai-for-developers-project-386/actions/workflows/hexlet-check.yml/badge.svg)](https://github.com/lukyanzhukov/ai-for-developers-project-386/actions)

Учебный проект «Календарь звонков»: небольшой сервис записи на встречи по мотивам [Cal.com](https://cal.com/). Проект разрабатывается совместно с ИИ-агентами — от проектирования до запуска в облаке.

Учебный проект Хекслета: https://ru.hexlet.io/programs/ai-for-developers
Как это должно работать: https://files.hexlet.app/a/2ipc5m

## Сценарий записи на звонок

Ниже описано целевое поведение. Сейчас доступны главная, создание типов встреч в `/admin` и публичный список `/booking`; сама запись ещё не реализована. Владелец календаря один и задан заранее. Владелец и гость пользуются сервисом без регистрации и авторизации.

1. **Владелец создаёт тип встречи.** В разделе «Админка» он указывает название, необязательное описание и длительность. ID назначает система, либо его задаёт владелец. В форме доступны 15, 30, 45, 60, 90 и 120 минут (по умолчанию 30) и ручной ввод от 1 до 1440 минут. После сохранения тип сразу появляется на публичной странице записи. Совпадающее название вызывает предупреждение со ссылками на существующие типы, но не запрещает создание; занятый ID вызывает ошибку без перезаписи.
2. **Гость выбирает тип встречи.** На главной странице он нажимает «Записаться», видит доступные типы с описанием и длительностью и открывает нужный.
3. **Гость выбирает дату и время.** Календарь показывает доступность на ближайшие 14 календарных дней. Для выбранной даты гость выбирает свободный слот длительностью выбранного типа встречи и нажимает «Продолжить». Занятое время недоступно для выбора; если свободных слотов нет, можно выбрать другую дату в пределах окна.
4. **Гость подтверждает запись.** Он вводит имя и email, при желании добавляет заметку и отправляет форму. Обязательные имя и email — наше проектное решение для идентификации гостя, а не требование исходного задания. Перед сохранением сервер повторно проверяет доступность. Если время уже заняли, приложение сообщает об этом и предлагает выбрать другой слот.
5. **Гость видит подтверждение.** После успешного сохранения приложение показывает тип встречи, дату, время начала и окончания и часовой пояс. Занятый интервал становится недоступен для записи на встречи всех типов, включая слоты с частичным пересечением. Выбор слота сам по себе запись не создаёт.
6. **Владелец видит новую встречу.** В «Админке» запись появляется в общем списке предстоящих встреч всех типов: тип, дата и время, имя и email гостя, заметка, если она есть.

## Границы и правила проекта

- Окно записи включает сегодня и следующие 13 календарных дней в `Asia/Novokuznetsk` и сдвигается в полночь. Рабочие дни — понедельник–пятница, 09:00–18:00; старты каждые 15 минут от начала рабочего дня. Праздники, перерывы и исключения не учитываются. Гость видит время владельца с явным часовым поясом.
- Слот длится столько, сколько выбранный тип встречи, и целиком помещается в рабочие часы. Прошедшее время недоступно для записи.
- Занятость общая для всех типов: полные и частичные пересечения запрещены, в том числе при одновременных запросах. Из двух конфликтующих запросов успешен только один. Следующая встреча может начаться ровно в момент окончания предыдущей.
- Подтверждение записи показывается в приложении. Авторизация, личные кабинеты, внешние календари, создание ссылок на видеозвонок, email-рассылки, отмена и перенос встреч в текущий объём не входят.
- Для реализации выбрана память одного серверного процесса: перезапуск будет сбрасывать типы встреч, записи и результаты повторных запросов. Сохранность после перезапуска и несколько экземпляров сервера не поддерживаются. Повтор подтверждения с тем же ключом и данными возвращает ту же запись в пределах жизни процесса; другой набор данных с тем же ключом отклоняется.
- Список владельца включает будущие и текущие встречи всех типов до момента окончания, упорядоченные по началу, затем ID. Обновление при открытии и вручную; автоматического опроса, поиска, фильтров и истории нет.
- Обязательная цепочка API: TypeSpec-контракт → сгенерированная OpenAPI-спецификация → клиентский SDK фронтенда. До выбора стека нужно проверить наличие генератора клиента для языка фронтенда. Серверные типы и маршруты генерируются при поддержке фреймворком; иначе сервер реализуется по контракту и проверяется тестами.

Сценарий сверен с [руководством Cal.com по типам встреч](https://cal.com/blog/event-types-guide-calcom) и [документацией формы бронирования](https://cal.com/docs/platform/atoms/booker) 8 ноября 2026 года. Имя, email, необязательная заметка и экран подтверждения уточняют путь после выбора слота; расширенные возможности Cal.com не становятся требованиями проекта.

TypeScript 6, Node.js 24 LTS, Fastify 5; React 19, Vite и Mantine.
Тесты — Vitest и Playwright (Chromium), линтер — Oxlint, форматирование — oxfmt, Git-хуки — hk.
Версии окружения закреплены в `mise.toml`, зависимости — в `package.json` и `pnpm-lock.yaml`.

Каркас следует официальным руководствам [Fastify](https://fastify.dev/docs/latest/Guides/Getting-Started/),
[Vite](https://vite.dev/guide/) и [Mantine для Vite](https://mantine.dev/guides/vite/).
Инструменты проверок выбраны по [dev-quality-gates](https://github.com/mokevnin/dev-quality-gates)
(бывший dev-guardrails).

### Контракт и SDK

Реализованы `GET /api/health` → `200 { "status": "ok" }` и `GET /api/meeting-types` → `200 { "items": [...] }`.
Список типов упорядочен по времени создания от ранних к поздним, затем по ID. Пустой сервер возвращает `items: []`.
`api/main.tsp` — источник контракта; `@typespec/openapi3` выпускает OpenAPI 3.0,
`@hey-api/openapi-ts` — Fetch SDK, серверные типы и JSON Schema в `generated/`.
Дымовой тест и страница `/booking` обращаются к серверу через этот SDK. Главная остаётся статичной.

Согласованный контракт также описывает следующие операции; их обработчики и интерфейс пока не реализованы:

| Операция                                   | Успешный ответ                                                                    |
| ------------------------------------------ | --------------------------------------------------------------------------------- |
| `POST /api/meeting-types`                  | `201`, созданный тип                                                              |
| `GET /api/meeting-types/{id}/availability` | `200`, все 14 дат со слотами, включая пустые даты                                 |
| `POST /api/bookings`                       | `201`, запись; повтор с прежним `Idempotency-Key` и данными — `200`, та же запись |
| `GET /api/bookings`                        | `200`, будущие и текущие встречи всех типов                                       |

Поля, ограничения, ответы и ошибки заданы в `api/main.tsp`, поведение и критерии приёмки — в
[спецификации бронирования](https://github.com/lukyanzhukov/ai-for-developers-project-386/issues/9).
Ошибки имеют `code`, `message` и необязательный массив `fields` для ошибок отдельных полей.
Контракт различает ошибки данных (`400`), неизвестный тип (`404`), занятое время,
устаревший слот, выход из окна и конфликт ключа (`409`), внутреннюю ошибку (`500`).
Даты календаря относятся к поясу владельца, моменты начала и окончания передаются в UTC с `Z`.
Тест контракта проверяет ограничения OpenAPI и вызовы SDK с подставленным транспортом;
он не доказывает работу серверных операций. Список типов дополнительно проверяется через SDK по реальному HTTP и в Chromium против собранного приложения. Остальные операции будут проверяться при реализации.

```bash
mise run generate
```

Результаты генерации хранятся в Git. Не редактируйте `generated/` вручную.
`mise run check` повторяет генерацию и падает при любом расхождении, включая новые и удалённые файлы.
При расхождении команда оставляет заново сгенерированные файлы для проверки и коммита.
Генерируемый код исключён из линтера и форматтера, но участвует в проверке типов и сборке.

Проверка цепочки выявила два ограничения:

- Hey API 0.99.0 использует Compiler API TypeScript и не работает с TypeScript 7; закреплена совместимая версия 6.0.3.
- Fastify-плагин Hey API находится в Beta и фактически генерирует только типы обработчиков.
  Регистрация маршрутов написана вручную, типы обработчиков и JSON Schema ответов генерируются.
  У health нет тела и параметров запроса; схемы входных данных новых операций уже генерируются из контракта.

### Структура

- `api/` — TypeSpec-контракт.
- `generated/` — OpenAPI, SDK, серверные типы и JSON Schema.
- `server/` — Fastify и запуск приложения.
- `web/` — React и Mantine.
- `tests/` — проверки содержимого страниц и дымовой тест запуска собранного приложения.
- `scripts/` — воспроизводимая генерация и проверка новых сообщений коммитов.
- `docs/adr/` — принятые решения о модели записи, первой фиче и браузерных проверках.

## Установка

Установите [mise](https://mise.jdx.dev/getting-started.html) и активируйте его в оболочке.
Дальше всё окружение и команды проекта управляются через mise:

```bash
git clone https://github.com/lukyanzhukov/ai-for-developers-project-386.git
cd ai-for-developers-project-386
mise trust
mise install
mise run install
mise run check
```

`mise install` устанавливает закреплённые инструменты. Хук `postinstall` вызывает ту же задачу
`install`: установка зависимостей с frozen lockfile, Chromium Headless Shell для браузерных тестов
и установка Git-хуков через `hk install --mise`. Для браузера загружаются также необходимые
системные библиотеки; на Linux могут потребоваться права sudo.
Установка браузера следует [документации Playwright](https://playwright.dev/docs/browsers).
Launcher подготавливает закреплённое окружение даже без активированной оболочки.
Повторный `mise run install` безопасен и нужен, например, после обновления зависимостей в Git.
Вход в каталог сам по себе не запускает серверы и не переустанавливает зависимости.

## Использование

```bash
mise run dev       # запуск API и Vite в фоне через mise daemons / pitchfork
mise run status    # состояние обоих процессов
mise run logs      # логи процессов
mise run stop      # остановка обоих процессов
```

Интерфейс: <http://127.0.0.1:5173>. Vite проксирует `/api` на Fastify: <http://127.0.0.1:3000>.
На `/` расположена главная с описанием сервиса, правилами и тремя шагами записи.
Кнопка «Записаться» ведёт на `/booking`: страница загружает типы встреч, показывает название,
описание обычным текстом с сохранением пробелов и переносов и длительность в минутах.
Доступны состояния загрузки, пустого списка и ошибки с кнопкой «Повторить»; запрос ограничен 10 секундами.
Есть ссылка на главную; прямой переход и обновление `/booking` работают также после сборки.
Ссылка «Админка» ведёт на `/admin`: форма создаёт тип с названием (1–120 символов после удаления
крайних пробелов), необязательным описанием до 2000 символов и целой длительностью 1–1440 минут.
Доступны готовые варианты и ручной ввод, в том числе 17 минут. Пустой ID назначается как случайный UUID;
собственный ID после удаления крайних пробелов содержит 1–64 строчные латинские буквы, цифры и дефис,
начинается и заканчивается буквой или цифрой. Регистр автоматически не меняется.
Занятый ID показывает ошибку с сохранением формы; совпадающее название без учёта регистра вызывает
неблокирующее предупреждение с описаниями, длительностями и ссылками на элементы публичного списка.
После создания тип сразу опубликован. Создание доступно через SDK (`POST /api/meeting-types`);
ошибки возвращают согласованный код и сообщение, ошибки полей — также `fields`.
Данные хранятся в памяти одного процесса: рабочий сервер стартует пустым, перезапуск удаляет все типы.
Редактирование и удаление типов, календарь, подтверждение записи и список встреч владельца пока не реализованы.
Настройки `HOST`, `PORT`, `WEB_PORT` заданы в `mise.toml`; секреты для каркаса не нужны.
Для локальных переопределений используйте игнорируемый `mise.local.toml`.
При смене портов daemons также измените `ready_port` соответствующего процесса.
Daemons требуют `experimental = true`; версия pitchfork закреплена.
Серверы остаются запущенными после выхода команды `dev`, остановка — явно через `stop`.

Собранное приложение отдаёт API и фронтенд с одного адреса:

```bash
mise run build
mise run start     # http://127.0.0.1:3000, остановка Ctrl+C
```

### Проверки

```bash
mise run check          # генерация, hk: линтер/формат/workflow, типы, сборка, smoke, коммиты
mise run lint
mise run format:check
mise run typecheck
mise run test           # сначала сборка, затем Vitest без watch-режима
mise run fix            # исправления линтера и форматирование
```

Vitest автоматически находит `tests/**/*.test.ts`, выполняет тесты и сообщает результат.
Smoke-тест запускает собранное приложение на свободном порту, проверяет
HTTP 200 и ответ через SDK, HTML главной и `/booking`, доступность JS фронтенда, затем завершает сервер.
Таймауты и очистка процесса работают и при ошибке. Отдельные тесты рендерят React в HTML
и проверяют описание сервиса, ссылки и начальную загрузку списка.
В том же smoke-тесте Playwright открывает собранное приложение в Chromium на экранах
1280 × 900 и 390 × 844: проверяет переход «Записаться» → `/booking` → «На главную»,
обновление `/booking` и отсутствие горизонтальной прокрутки на обеих страницах.
Дополнительные HTTP- и браузерные тесты запускают собранный сервер с управляемыми типами
через фабрику приложения: проверяют пустой и непустой список, порядок, одинаковые названия,
17 минут, безопасный вывод описания, загрузку, ошибку и повторный запрос. Тестовые данные
передаются только тестовым запуском; в рабочем сервере тестовые данные не создаются.
Создание проверяется через реальный HTTP/SDK: ограничения полей, строгие типы и null,
ошибочный JSON, одинаковые названия и сохранность списка при ошибках. Браузер проверяет
«Админка → создание → публичный список», предупреждение и ссылку, конфликт ID с сохранением формы
и ручную длительность 17 минут. Браузер и сервер завершаются и при ошибке.
Запись пока не реализована и не тестируется.

hk выполняет быстрые проверки изменённых файлов перед коммитом, включая форматирование CSS, commitlint — в `commit-msg`,
полный `mise run check` — перед push. Проверки не исправляют файлы автоматически.
Новый workflow `.github/workflows/ci.yml` вызывает тот же `mise run check` на каждый push.
Учебный `hexlet-check.yml` сохранён без изменений. Actions закреплены по SHA; права CI — только чтение.

### Сообщения коммитов

Используем [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/):
`<type>(<необязательная область>): <описание>`.
Типы: `feat`, `fix`, `docs`, `refactor`, `test`, `build`, `ci`, `chore`, `style`, `perf`, `revert`.
Для несовместимых изменений — `!` или footer `BREAKING CHANGE:`.

```text
chore: initialize application scaffold
ci: run mise checks
fix(api): handle invalid input
```

commitlint использует `@commitlint/config-conventional` (в том числе лимит заголовка 100 символов).
CI проверяет диапазон новых коммитов из `COMMIT_FROM` / `COMMIT_TO`;
локально проверяется история после коммита принятия соглашения, указанного в `scripts/check-commits.mjs`.
Старая история не переписывается. Формат сообщения не заменяет проверку его смысла.

База данных, Docker, авторизация, бронирование, coverage-порог и E2E полного сценария
в этот шаг не входят. Knip, архитектурные ограничения и syncpack отложены до появления
соответствующей структуры; отдельные конфигурационные валидаторы пока перекрываются
компиляторами, hk и линтером workflow. Сканеры секретов, уязвимостей и бот обновлений
рассмотрены, но будут подключаться отдельно: сетевые проверки не входят в текущий `check`.
