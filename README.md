# Календарь звонков

[![hexlet-check](https://github.com/lukyanzhukov/ai-for-developers-project-386/actions/workflows/hexlet-check.yml/badge.svg)](https://github.com/lukyanzhukov/ai-for-developers-project-386/actions)

Сервис записи на встречи с одним владельцем календаря. Учебный проект [Хекслета](https://ru.hexlet.io/programs/ai-for-developers) по мотивам [Cal.com](https://cal.com/).
[Исходное задание](https://files.hexlet.app/a/2ipc5m).

## Сценарий записи на звонок

1. Владелец создаёт тип встречи в `/admin`: название, описание и длительность от 1 до 1440 минут. ID можно задать вручную или оставить автоматическим.
2. Гость открывает `/booking`, выбирает тип встречи, дату и свободное время, вводит имя и email. Заметка необязательна.
3. После подтверждения гость видит детали записи. Занятое время становится недоступно для всех типов встреч.
4. Владелец просматривает текущие и будущие встречи в `/admin?view=bookings`. По умолчанию открыт полный список всех типов встреч с группировкой по датам, включая даты за пределами окна записи в 14 дней. Переключатель «Список / Календарь» открывает просмотр выбранного дня; выбранная дата сохраняется при переключении режимов, дополнительных запросов при этом нет. Данные обновляются при открытии и кнопкой «Обновить»; обновление сохраняет режим просмотра. Перезагрузка страницы возвращает режим «Список». При ошибке обновления ранее загруженные встречи остаются с предупреждением о возможной неактуальности. Завершённые встречи исчезают после успешного обновления; автоматического обновления по таймеру нет.

## Правила и ограничения

- Окно записи — сегодня и следующие 13 календарных дней в `Asia/Novokuznetsk`. Рабочее время: Пн–Пт, 09:00–18:00, начало слотов каждые 15 минут. Праздники и перерывы не учитываются.
- Встреча целиком помещается в рабочее время и начинается строго позже текущего времени сервера. Пересечения запрещены; следующая встреча может начаться сразу после предыдущей.
- Сервер повторно проверяет доступность при подтверждении. Из двух конфликтующих запросов успешен один. Повтор с тем же ключом и данными возвращает сохранённую запись.
- **Данные хранятся в памяти одного процесса и теряются при перезапуске или деплое.** Запускайте один экземпляр сервера.
- **Авторизации нет: админка и контактные данные гостей доступны всем.** Используйте вымышленные персональные данные.
- Нет редактирования и удаления типов, отмены и переноса встреч, email-уведомлений, интеграций с календарями и видеозвонками.

## Локальный запуск

Установите [mise](https://mise.jdx.dev/getting-started.html), затем:

```bash
git clone https://github.com/lukyanzhukov/ai-for-developers-project-386.git
cd ai-for-developers-project-386
mise trust
mise install
mise run dev
```

`mise install` устанавливает инструменты и через хук `postinstall` запускает `mise run install`: зависимости по lockfile, Chromium для тестов и Git-хуки hk. После обновления зависимостей повторите `mise run install`. На Linux установка системных библиотек Chromium может потребовать sudo.

Интерфейс: <http://127.0.0.1:5173>, API: <http://127.0.0.1:3000>. Vite проксирует `/api` на сервер.

```bash
mise run status   # состояние фоновых серверов
mise run logs     # логи
mise run stop     # остановка
```

`HOST`, `PORT` и `WEB_PORT` заданы в `mise.toml`. Локальные переопределения храните в игнорируемом `mise.local.toml`; при смене портов обновляйте `ready_port` процессов.

Собранное приложение отдаёт интерфейс и API с одного адреса:

```bash
mise run build
mise run start    # http://127.0.0.1:3000, остановка Ctrl+C
```

## Разработка

TypeScript, Node.js, Fastify; React, Vite и Mantine. Версии инструментов — в `mise.toml`, зависимости — в `package.json` и `pnpm-lock.yaml`.

- `server/` — сервер и хранение данных в памяти.
- `web/` — интерфейс.
- `api/main.tsp` — контракт TypeSpec.
- `generated/` — OpenAPI, Fetch SDK, серверные типы и JSON Schema.
- `tests/` — тесты Vitest, HTTP-проверки через SDK и браузерные сценарии Playwright.
- `scripts/` — генерация и проверки коммитов и деплоя.
- `GLOSSARY.md`, `docs/adr/` — термины и решения; `AGENTS.md` — инструкции для агентов.

Цикл разработки и артефакты описаны в [правилах трекера](docs/agents/issue-tracker.md#workflow-and-artifacts). При разборе идеи агент предлагает, стоит ли проверить её на макетах до спецификации. Этот этап включается только по вашему явному согласию: макеты проходят итерации ревью и приёмку, затем согласованный дизайн учитывается в спецификации и GitHub-задачах.

### API

| Метод | Путь                                   | Назначение                               |
| ----- | -------------------------------------- | ---------------------------------------- |
| GET   | `/api/health`                          | Проверка готовности: `{"status":"ok"}`   |
| GET   | `/api/meeting-types`                   | Список типов встреч                      |
| POST  | `/api/meeting-types`                   | Создание типа встречи                    |
| GET   | `/api/meeting-types/{id}/availability` | Свободные слоты                          |
| POST  | `/api/bookings`                        | Подтверждение записи с `Idempotency-Key` |
| GET   | `/api/bookings`                        | Будущие и текущие встречи всех типов     |

Поля, ограничения и ответы описаны в [api/main.tsp](api/main.tsp). Даты календаря относятся к часовому поясу владельца, моменты начала и окончания передаются в UTC.

После изменения контракта выполните `mise run generate` и закоммитьте `generated/`. Эти файлы не редактируют вручную. `mise run check` повторяет генерацию и выявляет расхождения, оставляя обновлённые файлы для проверки.

Маршруты Fastify зарегистрированы вручную: генератор Hey API выпускает типы обработчиков и схемы, но не регистрацию маршрутов.

### Проверки и коммиты

```bash
mise run check          # генерация, линтер, форматирование, workflow, типы, тесты и коммиты
mise run test           # сборка и Vitest, включая Chromium
mise run lint
mise run format:check
mise run typecheck
mise run fix            # автоисправления и форматирование
```

hk проверяет изменённые файлы перед коммитом, commitlint — сообщение коммита, полный `check` выполняется перед push и в CI. Формат сообщений — Conventional Commits, например `feat: запись на свободный слот (#12)`.
Учебный `.github/workflows/hexlet-check.yml` и имя репозитория сохраняйте без изменений.

### ИИ-ревью PR

Workflow `.github/workflows/opencode-pr-review.yml` запускает OpenCode для открытых PR из этого репозитория от владельца или `opencode-agent[bot]`, кроме draft. Для работы нужен Actions secret `OPENCODE_API_KEY`; комментарий публикуется через встроенный `GITHUB_TOKEN`.

Во всех трёх workflow OpenCode (ревью PR, команды `/oc` / `/opencode` и triage задач) основная и вспомогательная модели явно заданы как `opencode/big-pickle`, генерация заголовка отключена. Это исключает автоматический выбор платной вспомогательной модели. Изменения workflow для обычных комментариев `/oc` и triage вступают в силу после попадания в `main`; команду в комментарии к строке PR можно проверить на версии workflow из PR.

Лимит команды ревью — 7 минут, всего job — 10 минут. Агент ограничен пятью итерациями с переходом к текстовому отчёту; генерация заголовка отключена. Веб-поиск, загрузка внешних страниц и делегирование запрещены; состояние CI читается один раз, логи самого ревью не запрашиваются. Связанные задачи агент читает только по явным ссылкам из описания PR и комментариев человека; при отсутствии ссылок сообщает об этом и продолжает проверять diff.

Критерии и формат ревью описаны в [REVIEW.md](REVIEW.md). Workflow уже передаёт агенту указание прочитать этот файл вместе с `AGENTS.md`. Результат появляется комментарием в PR; автоматическое ревью не заменяет проверки CI и пользовательскую приёмку.

### Выпуски

После push в `main` workflow `release-please.yml` готовит release-PR с версией и `CHANGELOG.md`. После его слияния создаёт тег и GitHub Release. Публикации в npm и деплоя в этом workflow нет.

В Settings → Actions → General включите **Allow GitHub Actions to create and approve pull requests**. Используется встроенный `GITHUB_TOKEN`.
Созданный им release-PR не запускает CI автоматически: перед слиянием выполните `mise run check` на его ветке.

## Docker и Render

[Публичный сервис](https://call-calendar-386-o6lw.onrender.com).

Если сервис не открывается из РФ, попробуйте VPN: доступность может зависеть от провайдера и маршрута. Причина сетевых таймаутов при проверке не установлена; необходимость VPN — предположение.

```bash
docker build -t call-calendar:production .
docker run --rm --name call-calendar -e PORT=8080 -p 8080:8080 call-calendar:production
```

Адрес: <http://localhost:8080>. Контейнер слушает `0.0.0.0`, порт задаётся через `PORT` (по умолчанию 3000). Проверка готовности — `/api/health`. Остановка: `docker stop call-calendar`.

Для Render используйте Dockerfile из корня, один экземпляр и проверку `/api/health`. У сервиса с публичным Git URL после push нужно отдельно запустить деплой; для автоматического деплоя подключите репозиторий через Git provider credentials. Проверяйте SHA коммита и статус `live`.

Адрес MCP задан в `.codex/config.toml`. Для подключения выполните `codex mcp login render`, завершите OAuth и перезапустите сессию агента. Секреты храните вне Git.

Проверка работающего сервиса:

```bash
DEPLOYMENT_URL=https://call-calendar-386-o6lw.onrender.com mise run deployment:check
```

Команда проверяет создание типа, запись гостя, отказ при конфликте и список владельца. Она добавляет синтетические данные; нужен свободный слот в ближайшие 14 дней.

## Плановые аудиты

Два независимых GitHub Actions workflow работают на `main`: `todo-audit.yml` ищет
подтверждённые TODO/FIXME по понедельникам в **02:17 UTC / 09:17 Asia/Novokuznetsk**;
`lockfile-audit.yml` проверяет `pnpm-lock.yaml` ежедневно в **01:37 UTC / 08:37
Asia/Novokuznetsk**. Запуски одного аудита сериализованы без отмены предыдущего;
разные аудиты друг друга не ждут. Расписание GitHub может запускаться с задержкой.

OpenCode **1.19.5** по умолчанию использует бесплатную `opencode/big-pickle` для
`model` и `small_model`, генерация заголовка отключена. При ручном запуске input
`model` позволяет выбрать `opencode/mimo-v2.6-flash-free`; другие ID скрипт
отклоняет до запуска агента. Выбранная модель фиксируется в `agent-status.json`.
Автоматических повторов с другой моделью нет. Бесплатная квота определяется
провайдером: её исчерпание означает ошибку анализа, а не успешный аудит.
Нужен repository secret
`OPENCODE_API_KEY`. Агент получает снимок как недоверенные данные; инструменты,
изменения файлов и исполнение команд запрещены. У job анализа только
`contents:read`, `issues:read`, `actions:read`; `issues:write` есть только у
отдельного publisher с `GITHUB_TOKEN`. OpenCode App и дополнительные write-токены
не нужны. Все Actions закреплены полными SHA, OSV Scanner **2.7.1** — SHA256
проверенного Linux-бинарника. Ни один аудит не меняет зависимости или lockfile.

TODO/FIXME извлекаются из tracked source на SHA запуска с путём, строкой и
контекстом. Generated/vendor/build/node_modules, навыки и учебные тексты исключены;
агент отклоняет учебные, устаревшие и неподтверждённые пометки с объяснением.
OSV сохраняет исходный JSON, stderr, exit code и число пакетов (`--all-packages`).
Код `0` означает чистый результат, `1` — находки: агент сначала оформляет отчёт,
затем job аудита завершается ошибкой, а publisher обрабатывает подтверждённые
находки. `127` — ошибка сканера, `128` — нет распознанных пакетов; остальные коды,
таймауты, пустой или некорректный ответ агента тоже дают ошибку с диагностикой,
без выдуманной уязвимости. Отсутствие кандидатов создаёт пустой валидный отчёт.
OpenCode запускается с явным `--dir`, cwd и `PWD` каталога артефактов; снимок
передаётся через stdin. JSONL и INFO-логи сохраняются по мере поступления в
`agent.jsonl` и `agent.stderr`, статус — в `agent-status.json`. Значения переменных
окружения с `TOKEN`, `SECRET`, `PASSWORD`, `KEY`, `CREDENTIAL`, `AUTH` в имени
и заголовки авторизации скрываются в диагностике.
Ошибка провайдера (например, исчерпанный лимит или неверный API key) либо JSONL
событие `error` немедленно завершает процесс агента вместе с его дочерними
процессами; общий таймаут остаётся 420 секунд. Причину конкретного сбоя следует
смотреть в этих артефактах; ошибка агента не переключает аудит на платную модель.

Publisher просматривает все страницы открытых и закрытых issues и комментариев,
включая ручные задачи. Ключ TODO — путь и текст без номера строки; ключ OSV —
экосистема, пакет, версия и группа пересекающихся advisory aliases. Маркеры в
issues/комментариях хранят идентичность и fingerprint фактов, без времени и URL
запуска. Одинаковые сведения повторно не публикуются; новые сведения добавляют
один комментарий в существующую задачу, включая закрытую. Автозакрытия и reopen
нет. Пробелы и пустые строки вокруг неизменной TODO-пометки не считаются
новыми фактами; содержательные изменения контекста учитываются. Для ручной OSV-задачи
без fingerprint publisher консервативно выбирает `skip`: новые факты нельзя
доказать сравнением с исходным снимком. Перефразирование ответа агента не служит
основанием для комментария; при наличии fingerprint сравниваются факты OSV.
Решение `create`/`comment`/`skip`, причина, fingerprint и связанные URL
сохраняются в `decisions.json`. Ошибка API делает job публикации неуспешным.

Результаты доступны в summary и artifacts (30 дней): `todo-audit-input` /
`osv-audit-input` содержат `input.json`; `*-audit-report` — результат агента,
Markdown и сырую диагностику; `*-audit-publication` — решения publisher и его
диагностику. Artifacts загружаются также при ошибках. Отчёты не коммитятся.

После разрешённого слияния можно запустить каждый workflow вручную:

```bash
gh workflow run todo-audit.yml --ref main
gh workflow run lockfile-audit.yml --ref main
# Ручной выбор другой разрешённой бесплатной модели
gh workflow run todo-audit.yml --ref main -f model=opencode/mimo-v2.6-flash-free
gh workflow run lockfile-audit.yml --ref main -f model=opencode/mimo-v2.6-flash-free
```

Для повторной обработки сохранённого снимка укажите ID завершённого запуска
того же workflow в этом репозитории на `main` (пока его artifact не истёк):

```bash
gh workflow run todo-audit.yml --ref main -f source_run_id=123456789
gh workflow run lockfile-audit.yml --ref main -f source_run_id=123456790 -f model=opencode/mimo-v2.6-flash-free
```

Replay сохраняет в снимке `originRunId` исходного запуска отдельно от текущего
запуска обработки и проверяет SHA снимка по исходному запуску. Для источника
artifact и исходного запуска проверяются репозиторий, workflow, завершённость,
событие schedule/dispatch и ветка `main`; также проверяется схема снимка.
Поэтому цепочки replay работают и после продвижения `main`. Скачивается только
свой input artifact, данные анализируются заново с той же дедупликацией.
Publisher исполняет код из доверенного checkout `main`, не из artifact. Dispatch
из другой ветки пропускает оба job. Локальная проверка CLI и fake GitHub boundary:
`mise run audit:test` (также входит в `mise run check`).

Изолированная учебная проверка `ignoreUntil` запускается только вручную:

```bash
gh workflow run lockfile-audit.yml --ref main -f exercise_ignore_until=true
```

Она создаёт временные lockfile с одной уязвимой и исправленной версией вне
рабочего проекта, проверяет future/expired исключение с конкретным advisory и
причиной, сохраняет raw reports/exit codes в artifact. Часы и исключения рабочего
проекта не меняются. Для локального запуска: `node scripts/osv-ignore-lab.mjs
--scanner /absolute/path/to/osv-scanner --output /tmp/osv-ignore-lab`.

Демонстрация после отдельного разрешения слияния: повторить снимок и проверить
отсутствие дубликатов, затем сравнить `gh run cancel RUN_ID` (отмена одного
запуска) с `gh workflow disable todo-audit.yml` и `gh workflow enable
 todo-audit.yml` (выключение/включение будущих запусков). Эти команды здесь только
инструкция; фактические запуски, публикация issues и пользовательская приёмка
сообщаются отдельно.
